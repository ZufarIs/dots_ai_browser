# dots — инструкция пользователя

> Каждый ИИ-агент — это модель и браузер. Модель можно поменять флагом.
> Браузер — это то, что видит сайт.

`dots` — это CLI-обёртка над `invisible-playwright-mcp`, которая ставит
рядом два окна: диалог с моделью слева и живой браузер справа. Под капотом
— настоящий Firefox с антидетектом, патченный на уровне C++, и
OpenAI-совместимый клиент, который можно подключить к любому провайдеру
через `.env`.

## 1. Что это и зачем

`dots` запускает браузер, в котором одновременно:

- смотрит человек — окно браузера на правой панели;
- работает агент — модель видит страницу через инструменты и действует
  курсором и клавиатурой так, как это делал бы живой пользователь.

Это не «паук на стероидах». Браузер — настоящий Firefox, в котором:

- фингерпринт (экран, шрифты, GPU, часовой пояс, язык) согласован внутри
  себя, без расхождений, которые выдают автоматизацию;
- нет флага `WebDriver`, нет протокола DevTools, нет automation-глобалов в
  странице;
- курсор движется к точке клика и нажимаются клавиши по одной — каждый
  получаемый страницей event выглядит как обычный пользовательский;
- `--seed` даёт того же человека при каждом запуске, а `--profile-dir`
  хранит логины и cookies между запусками.

Модель — любая, что говорит по OpenAI Chat Completions API. По умолчанию
это OpenRouter, но `.env` переключает на что угодно.

## 2. Установка

`dots` написан на Python, распространяется через `uv` (`uvx` запускает
без установки).

### Windows (PowerShell)

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
$env:Path = "$env:USERPROFILE\.local\bin;$env:Path"
uvx --from git+https://github.com/feder-cr/dots dots --openrouter-key sk-or-...
```

### Linux / macOS

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env
uvx --from git+https://github.com/feder-cr/dots dots --openrouter-key sk-or-...
```

### Из локального чекаута (для разработки)

```bash
git clone https://github.com/feder-cr/dots
cd dots
uv sync
uv run dots --openrouter-key sk-or-...
```

Первый запуск скачивает движок браузера (~150 МБ) и кеширует его. На это
уходит 30–90 секунд; в терминале идёт одна обновляющаяся строка с
процентом. После этого запуск мгновенный.

## 3. Быстрый старт

Самый короткий путь — OpenRouter:

```bash
dots --openrouter-key sk-or-v1-xxxxxxxx
```

После старта откройте в браузере **http://127.0.0.1:8765**. Слева —
диалог, справа — браузер. Напишите задачу, нажмите Enter.

Чтобы не передавать ключ в командной строке, положите его в `.env` рядом
с тем местом, откуда запускаете:

```env
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxx
```

или используйте любой другой провайдер (см. следующий раздел).

## 4. Подключение модели

`dots` подключается к любому провайдеру, который отвечает на OpenAI
Chat Completions API. Конфигурация живёт в `.env` в директории, откуда
запускается команда.

### Где ключ лежит

Ключ — это свойство **человека**, а не папки. Поэтому он может лежать в
двух местах, и читаются они в таком порядке:

1. **`.env` проекта** — в той папке, откуда запущена команда. Побеждает:
   если проект задаёт свой ключ, он и используется.
2. **`.env` пользователя** — `%APPDATA%\invisible-playwright-mcp\.env`.
   Заполняет только то, чего нет в проекте.

Так `dots`, запущенный из любой папки, находит ключ, а проект со своим
`.env` всё равно имеет свой.

```bash
# один раз, для всех папок
mkdir -p "%APPDATA%\invisible-playwright-mcp"
copy .env "%APPDATA%\invisible-playwright-mcp\.env"
```

Лаунчер (`dots-gui`) читает `.env` из поля **Working directory** и
**помнит** эту папку между запусками: открытый из другой директории
лаунчер найдёт тот же проект и тот же ключ.

### 4.1. OpenRouter (по умолчанию)

Если ничего другого не настроено, `dots` использует OpenRouter.
Достаточно одного из:

- `--openrouter-key sk-or-...`
- переменная `OPENROUTER_API_KEY` в шелле или `.env`
- переменная `OPENAI_API_KEY` (зеркалится в `OPENROUTER_API_KEY`)

Идентификатор модели — `--model` или `INVISIBLE_MCP_MODEL`. По умолчанию
`z-ai/glm-5.3-flash`.

### 4.2. Любой OpenAI-совместимый провайдер через `.env`

Скопируйте `.env.example` в `.env` и заполните три переменные:

```env
OPENAI_API_KEY=sk-...
OPENAI_BASE_URL=https://api.example.com/v1
OPENAI_MODEL=model-name
```

- `OPENAI_API_KEY` — ключ провайдера. Зеркалится в `OPENROUTER_API_KEY`,
  чтобы встроенный клиент пакета нашёл его.
- `OPENAI_BASE_URL` — endpoint без хвостового слэша. Перебивает
  захардкоженный в пакете OpenRouter.
- `OPENAI_MODEL` — название модели у провайдера. Зеркалится в
  `INVISIBLE_MCP_MODEL`.

Когда `OPENAI_BASE_URL` задан, `dots` также убирает OpenRouter-заголовки
`HTTP-Referer` и `X-Title` из запросов — у другого провайдера они не
нужны и засоряют логи.

### 4.3. Примеры провайдеров

| Провайдер | `OPENAI_BASE_URL` |
|-----------|-------------------|
| OpenAI | `https://api.openai.com/v1` |
| DeepSeek | `https://api.deepseek.com/v1` |
| Together AI | `https://api.together.xyz/v1` |
| Groq | `https://api.groq.com/openai/v1` |
| Mistral | `https://api.mistral.ai/v1` |
| OpenRouter (явно) | `https://openrouter.ai/api/v1` |
| Ollama (локально) | `http://127.0.0.1:11434/v1` |
| llama.cpp server | `http://127.0.0.1:8080/v1` |
| vLLM (локально) | `http://127.0.0.1:8000/v1` |
| LM Studio | `http://127.0.0.1:1234/v1` |

Пример для локального Ollama:

```env
OPENAI_API_KEY=ollama
OPENAI_BASE_URL=http://127.0.0.1:11434/v1
OPENAI_MODEL=qwen2.5:14b
```

Ollama не проверяет ключ — подойдёт любая строка. Запустите модель
заранее: `ollama run qwen2.5:14b`.

### 4.4. Приоритет источников

Каждый параметр ищется так — первое выигрывает:

1. **Флаг командной строки** (например, `--openrouter-key sk-...`).
2. **Переменная в шелле** (например, `export OPENAI_API_KEY=...`).
3. **`.env`** в директории, откуда запущен `dots`.
5. Значение по умолчанию в самом пакете.

Никакая переменная из `.env` не перебивает то, что уже стоит в шелле —
это сознательно, чтобы случайно не подменить живой секрет старой записью.

## 5. Интерфейс пользователя

После запуска `dots` откройте `http://127.0.0.1:8765`. Двухпанельный
интерфейс:

```
+-----------------------+----------------------------+
|    Диалог / модель     |    Живой браузер           |
|    (слева)            |    (справа)                |
|                       |                            |
|  Список чатов         |   Скриншот страницы в      |
|  История              |   реальном времени.        |
|  Поле ввода           |   Кнопки навигации,        |
|                       |   стоп-задача, перезагрузка|
+-----------------------+----------------------------+
```

Каждый шаг агента виден в реальном времени:

- текст, который модель пишет;
- какой инструмент вызван (`browser_navigate`, `browser_click`,
  `browser_type`, ...);
- результат (текст страницы, скриншот);
- счётчик потраченных токенов.

Кнопка «Стоп» прерывает текущий шаг. Следующий запрос к модели не
уйдёт, но уже оплаченная половина ответа будет отброшена.

Слева — список сохранённых чатов. Каждый чат — это отдельная сессия со
своей историей, своим браузером и своим фингерпринтом.

## 6. Опции командной строки

Все опции применяются к подкоманде `ui` (это единственная команда `dots`):

```bash
dots [OPTIONS]
```

| Опция | Назначение |
|-------|------------|
| `--openrouter-key TEXT` | Ключ OpenRouter (или переменная `OPENROUTER_API_KEY`). |
| `--model TEXT` | Идентификатор модели (или переменная `INVISIBLE_MCP_MODEL`). По умолчанию `z-ai/glm-5.3-flash`. |
| `--host TEXT` | Адрес, на котором слушает интерфейс. По умолчанию `127.0.0.1` — только локальный. Не меняйте на `0.0.0.0`, если не понимаете зачем. |
| `--port INTEGER` | TCP-порт. По умолчанию `8765`. |
| `--proxy TEXT` | Прокси-сервер для браузера. Формат `http://user:pass@host:port` или `socks5://host:port`. |
| `--seed INTEGER` | Детерминированный seed фингерпринта. Один и тот же seed даёт одного и того же «человека» при каждом запуске. |
| `--headed` | Запустить браузер в видимом окне (по умолчанию headless). |
| `--binary TEXT` | Путь к конкретному бинарнику движка. Пропускает встроенный загрузчик. |
| `--profile-dir TEXT` | Папка для постоянного профиля — логины и cookies сохраняются между запусками. |
| `--help` | Показать справку и выйти. |

Пример:

```bash
dots \
  --openrouter-key sk-or-v1-xxx \
  --model anthropic/claude-sonnet-4.5 \
  --port 9000 \
  --seed 12345 \
  --profile-dir ~/dots-profiles/work
```

Кроме этого у `dots` есть подкоманды собственной сборки:

| Подкоманда | Назначение |
|------------|------------|
| `dots profile ...` | профили: список, показать, создать, изменить, удалить. |
| `dots auth ...` | сохранённые логины: список, показать, добавить, забыть. |
| `dots handover` | вопрос, на котором агент остановился. |
| `dots serve` | серверный режим: тот же браузер, но через API. См. раздел 16. |

| `INVISIBLE_MCP_MODEL` | Имя модели (оригинальное). |

| `INVISIBLE_MCP_SESSION_ID` | Какой сохранённый чат поднять (служебная, для встроенной логики). |

использовании.

## 8. Двухпалубный браузер: `main` и `support`

В каждый момент у агента есть ровно **два** браузера, не больше:

- **`main`** — это «вы». Его страница, его cookies, его логины, его
  фингерпринт. Здесь происходит работа.
- **`support`** — это помощник для всего, что **не должно** касаться
  вашей идентичности. Например, при регистрации где-то нужен одноразовый
  email для подтверждения: открываете `support`, идёте на сайт
  одноразовых почт, копируете адрес, вставляете его в форму в `main`,
  возвращаетесь в `support` за ссылкой. Один и тот же человек с двумя
  сайтами — это сигнал автоматизации; два разных фингерпринта — нет.

Правила:

1. Открывайте `support` через `browser_open` (`browser="support"`),
   когда задача этого требует.
2. Закрывайте `support` через `browser_close`, как только он больше не
   нужен, **до** того, как дадите ответ. Это реальный браузер; он не
   сохраняется; он пропадает с остановкой сервера.
3. Никакого третьего браузера нет. Если нужна ещё одна страница — это
   снова `support`.

Каждый инструмент принимает аргумент `browser` (`main` или `support`).
Если его не указать — действие идёт в `main`.

## 9. Антидетект: fingerprint, seed, proxy, profile

`dots` подменяет фингерпринт на уровне движка, не поверх JavaScript-ом
(который сайт может проверить).

### seed

`--seed N` — детерминированное число, из которого выводится весь
фингерпринт: разрешение экрана, шрифты, GPU-вендор, часовой пояс, язык.
Один и тот же seed даёт того же «человека» при каждом запуске, на любой
машине.

```bash
dots --seed 42
```

### proxy

`--proxy URL` — выход в интернет через указанный прокси. При смене
прокси `dots` подтянет часовой пояс и язык под выход — это не два
разрозненных параметра, которые сайт сопоставляет, а согласованная
идентичность.

```bash
dots --proxy http://user:pass@example.com:8080
dots --proxy socks5://127.0.0.1:1080
```

### profile

`--profile-dir PATH` — папка, в которой хранятся cookies, логины и
настройки браузера между запусками. Полезно, когда нужно снова
залогиниться.

```bash
dots --profile-dir ~/.dots/profiles/work
```

`profile` хранит и `seed`, так что повторный запуск с тем же профилем
вернёт ту же личность.

### Профили `dots`: имя вместо длинной команды

Папка, прокси и seed — это всегда одна и та же связка для одного и того же
человека. Держать их в памяти и набирать каждый раз неудобно, поэтому у
`dots` есть реестр: **профиль** — это имя, под которым хранится всё
сразу.

```bash
dots profile add work --label "Рабочий" \
    --proxy http://user:pass@example.com:8080 --seed 4242 \
    --workdir ~/work/shop

dots profile list
dots profile show work
dots --profile work          # запустить интерфейс под этим именем
```

Внутри профиль хранит:

| Поле | Что это |
|------|---------|
| каталог браузера | cookies, логины, seed — то же, что `--profile-dir` |
| рабочая папка | куда агент складывает результаты работы для этого профиля |
| прокси | выход в интернет |
| seed | личность (фингерпринт) |
| устройство (пины) | какой экран и какое соотношение пикселей заявляет профиль |
| порт | на каком порту живёт интерфейс этого профиля |
| заголовок, заметка | для вас, не влияет на работу |

Где это лежит:

```
<HOME>/invisible-playwright-mcp/profiles/
├── index.json              список профилей
└── work/
    ├── browser/            каталог профиля Firefox
    ├── work/               рабочая папка
    └── auths.json          логины (см. ниже)
```

⚠️ **Смена seed у уже запускавшегося профиля.** Каталог профиля помнит, кем
он был, поэтому профиль, который уже открывали, не примет другой seed —
следующий запуск откажется. Это защита от входа на сайт с «другого
компьютера». Если нужно начать с нуля — удалите
`<каталог профиля>/.stealth-identity.json`.

Seed живёт в двух местах: в реестре (`dots profile set NAME --seed N`) и в
каталоге профиля (`.stealth-identity.json`, его пишет движок при первом
открытии). Побеждает **каталог** — там cookies и логины, и браузер, пришедший
под чужим seed, принёс бы их с другой машины. Поэтому `dots` передаёт
движку именно тот seed, который помнит каталог, и `dots profile show`
показывает его же:

```
  seed            1361434516
  device          1920x1080, ratio 1.0, frame 0x85, taskbar 48
  ! the browser directory remembers seed 1361434516, the registry says 8345.
```

Строка с `!` — это и есть расхождение двух записей. Оно не мешает
работать: каталог и так главный. Но если в реестре лежит seed, который вы
забыли поставить, — это он и есть, и `dots profile show` его покажет.

Приоритет тот же, что и у всего остального:

```
--profile-dir (написан руками) > --profile ИМЯ > DOTS_PROFILE в .env > ничего
```

То есть `--profile work` — это просто удобная запись для `--proxy ... --seed
... --profile-dir ...`. Если указать `--profile-dir` руками, он победит.

### Устройство: экран, соотношение пикселей, рамка окна

Seed выводит **всю** личность целиком: экран, GPU, число ядер, кодеки. Он
согласован сам с собой — но не с машиной, на которой браузер запущен.

Из этого следует две вещи, которые чинит `dots`.

**1. Масштаб текста машины попадал в `devicePixelRatio`.** Движок пишет
соотношение пикселей в преф `layout.css.devPixelsPerPx` строкой, а потом
умножает его на масштаб текста **той машины, на которой он работает**.
Профиль заявлял `1.0`, а страница читала `1.1538461538461537` — на этой
машине. Расхождение считается одним делением, то есть это самая грубая
нестыковка из возможных. `dots` теперь выключает масштаб машины числом
(`ui.textScaleFactor = 100`), и страница читает ровно то, что заявляет
профиль.

**2. Геометрия окна.** Движок объявляет её целиком: внешнее окно — это
экран, внутреннее — внешнее минус рамка, высота — экран минус панель задач.
Пока префы доезжают, всё сходится. Не доезжают — и страница получает
настоящее окно (1678 пикселей на ноутбуке с масштабом 115 %) при
внутренней ширине 1920, взятой из профиля. Внешнее меньше внутреннего —
несуразица, которую умный скрипт отметит.

**Пины.** То, что seed менять нельзя: новый seed — новый человек, а логин
должен прийти с той же машины. Поэтому у профиля есть **пины** — что именно
этот человек заявляет об экране:

```bash
dots profile set work --pin screen.width=1920 --pin screen.dpr=1.25
dots profile show work        # показывает, что получилось
```

Словарь пинов принадлежит движку: неизвестное имя он называет сам, вместе
с теми, которые знает. Пиновать можно и `screen.chrome_w`, `screen.chrome_h`,
`screen.taskbar_px`, `screen.window_x`, `screen.window_y`, `screen.color_depth`
и остальное, что движок умеет.

**Проверка.** После запуска браузер измеряется: движку сказали одно, страницу
спросили, ответили ли они одно и то же. Расхождение печатается в лог
интерфейса, а агент может спросить и сам — tool `dots_profile_check`
(он открывает свою страницу, спрашивает и закрывает её).

```bash
dots profile show work        # что профиль заявляет (это же проверяется при старте)
```

Если расхождение есть, его видно в логе сразу при открытии браузера:
`device: devicePixelRatio is 1.1538..., the profile declares 1.0`.

⚠️ **Пин меняет то, что seed нарисовал.** Движок честно предупреждает, что
пин разрывает его байесовскую связность: класс GPU выводится из экрана, и
прибитый экран без соответствующего GPU — это уже другая связка. Поэтому
`screen.width`/`screen.height` лучше пинить вместе с `gpu.class_tier`, а
`screen.dpr`, `screen.chrome_*` и `screen.taskbar_px` — свободно: они ни на
что другое не влияют.

### В окне (dots-gui)

Всё это есть в окне, без командной строки.

**Поле «Device:»** — пины профиля. Пустое поле = «как нарисует seed».
Рядом — кнопка **Check**: она спрашивает у работающего сервера, что
браузер отвечает, и пишет ответ в лог и в строку под полем.

**Строка под полем** — то, что пины и seed дают вместе: экран, соотношение
пикселей, рамка окна, панель задач. И отдельно — если браузер помнит seed, а
реестр говорит другой, строка скажет об этом: каталог главный.

Всё это работает и без нажатий: при каждом открытии браузера `dots`
измеряет его и пишет в лог

```
device: the browser is the device the profile declares (1920x1080, ratio 1.0)
```

а если не совпало —

```
device: devicePixelRatio is 1.4286, the profile declares 1.25
```

### В веб-панели (127.0.0.1:8765)

То же самое — в шапке панели браузера, справа:

```
device 1920x1080, ratio 1.0, frame 0x85, taskbar 48   [edit] [check]
```

* **edit** — открывает поле для пинов прямо в панели; **save** записывает их
  в профиль.
* **check** — спрашивает открытый браузер, что он отвечает, и показывает
  ответ в этой же строке. Если браузер не открыт — так и скажет.

### Два профиля одновременно

Профили полностью независимы: у каждого свой браузер, своя переписка, своя
память агента, свои логины и свой порт. Запустить два — значит запустить
два:

```bash
dots profile set work --port 8801
dots profile set play --port 8802

dots --profile work     # http://127.0.0.1:8801
dots --profile play     # http://127.0.0.1:8802
```

В GUI: кнопка **Start all profiles** поднимает сервер для каждого профиля,
каждый на своём порту. Профилю без порта порт выдаётся и **записывается в
профиль** — в следующий раз он уже есть. Строки лога помечены именем
профиля, чтобы было видно, кто что пишет.

Порядок портов: `--port` в командной строке > порт профиля > 8765.

⚠️ **Что было сломано и теперь исправлено.** Пакет называет каждую беседу
`default` — одинаково во всех процессах. И переписка, и сохранённая личность
браузера называются по ней. Поэтому два профиля были **одной беседой с
одним браузером**: второй из запустившихся читал сохранённую личность
первого — seed, выход и каталог профиля — и открывал **тот** браузер. Оба
писали в один файл переписки поверх друг друга.

Теперь имя беседы включает профиль: `default-work` и `default-play`. Файлы
получаются разные, и разделяются не только браузеры, но и контекст агента.

Чтобы запускаться под одним и тем же профилем из одного каталога, допишите
в `.env`:

```bash
DOTS_PROFILE=work
```

### Логины и пароли, которые агент может использовать

Профиль браузера помнит cookies. Но он **не помнит пароль** от формы,
которую не до конца отправили, и не умеет ответить «а какой пароль у
рабочего аккаунта». Для этого в каждом профиле есть отдельный список —
`auths.json`. Агент сам его читает и сам вводит логин и пароль в форму,
когда страница просит войти.

```bash
dots auth add work https://shop.example.com alice 'мой-пароль'
dots auth list work
dots auth get work shop.example.com
dots auth remove work shop.example.com
```

Сайт определяется по хосту: `example.com`, `https://example.com/login?x=1`
и `WWW.Example.com` — это всё один и тот же `example.com`. Логин,
сохранённый для `example.com`, найдётся и на `id.example.com`.

В GUI (`dots-gui`) то же самое — таблица «Authorizations» под списком
профилей.

⚠️ **Пароли хранятся как есть.** Никакого шифрования, никакого
DPAPI/keyring. Что сделано — файл закрыт от «остальных» правами `600`
(на POSIX), он лежит отдельно от списка профилей, и ни одна команда
нигде не печатает пароль — `dots auth list` показывает вместо него
`....`. Это ровно та же модель, что и ключ API в `.env`. Если пароль
лежит ещё и в профиле Firefox — там он тоже в открытом виде.

Когда агент читает пароль, он получает его **только для того, чтобы
ввести его в форму**. В ответе пользователю пароль попасть не должен.

### Как агент это использует

Агенту доступны инструменты `dots profile …` и `dots auth …` (в MCP-клиенте
— с префиксом `mcp__stealth__`). Он сам решает, когда они нужны:

| Инструмент | Что делает |
|------------|-----------|
| `dots_profile_list` | какие профили сохранены |
| `dots_profile_show` | подробности одного профиля |
| `dots_profile_use` | закрыть браузер и открыть его под именем |
| `dots_profile_save` | создать/изменить профиль |
| `dots_profile_check` | проверить, что браузер — то самое устройство, что заявляет профиль |
| `dots_auth_list` | сайты с сохранёнными логинами (без паролей) |
| `dots_auth_get` | логин и пароль для одного сайта |
| `dots_auth_signin` | заполнить форму входа и нажать кнопку |
| `dots_auth_save` | запомнить логин |
| `dots_auth_forget` | забыть логин |

Логины читаются **из того профиля, под которым открыт текущий браузер** —
переключили профиль через `dots_profile_use`, переключился и список. Отдельного
аргумента «с какого профиля читать» у инструментов нет, так что случайно
прочитать чужой пароль нельзя.

`dots_profile_use` не создаёт третий браузер: он закрывает текущий и
открывает заново под нужным именем. Браузеров по-прежнему ровно два —
`main` и `support`.

### Первый запуск молчит

При первом запуске на машине `dots` читает все файлы библиотеки модели и
MCP-фреймворка впервые — а если на компьютере есть антивирус, он проверяет
каждый файл. На этой машине это занимало **55 секунд**, и всё это время в
логе было пусто.

Теперь:

* сервер печатает `dots    starting: ...` в первую секунду;
* лаунчер пишет `starting <профиль> on port <порт>...` до того, как процесс
  вообще запущен;
* прогрев файлов идёт в фоне отдельными процессами, пока вы читаете окно.

⚠️ **БАЙТКОД.** `uv` по умолчанию **не компилирует** байткод, и каждый
импорт тогда компилирует модули заново — на этой машине `import openai`
занимал 63 секунды вместо девяти. Если `dots` вдруг стал очень медленным:

```bash
python -m compileall -q .venv/Lib/site-packages
```

и при установке:

```bash
uv tool install --force --editable --compile-bytecode .
```

Флаг `--compile-bytecode` делает то же самое при установке.

### Прокрутка в живой панели

Живая панель справа — это **видео** окна браузера, а не сам браузер. Пакет
передаёт из панели в браузер **ничего**: ни клика, ни колеса, ни клавиши.
Поэтому прокрутить страницу, которую вы смотрите, было нечем, а часть
страницы ниже первого экрана была видна только агенту.

`dots` это закрывает: **колесо мыши над картинкой прокручивает страницу в
браузере**. Настоящим событием колеса (движок, а не `window.scrollBy`),
поэтому сайт не отличает прокрутку от скрипта.

* колесо — вверх/вниз;
* **Shift + колесо** — влево/вправо;
* прокрутка работает и по горизонтали, если страница шире экрана.

Агент при этом не теряет управление: прокрутка и его собственные действия
сериализованы одной блокировкой браузера. Если агент сейчас работает,
колесо подождёт его хода.

Прокрутка в панели **не отменяет** прокрутку самой страницы интерфейса:
колесо над перепиской листает переписку, как и раньше.

### Что ещё можно делать из интерфейса

* **Клик по картинке** в живой панели выбирает, какой браузер смотреть
  (`main` или `support`), — но не кликает по странице. Настоящие клики
  делает агент: это его браузер, и его действия видны в переписке.
* **Адресная строка** над панелью показывает, где сейчас браузер.
* **Запрос агента** (кнопка «Ask the agent») — вторая половина вмешательства
  оператора: см. раздел про `dots_ask_operator`.

### Вмешательство оператора

Иногда страница требует человека, а не модели. Код из аутентификатора, SMS,
подтверждение платежа, 3-D Secure, CAPTCHA, пароль, который здесь не
сохранён. Правильный ответ на такое — **остановиться и спросить**, а не
пытаться сильнее и не писать «задача невыполнима».

Агент так и делает: вызывает `dots_ask_operator` с вопросом и тем, что
конкретно нужно, и **заканчивает turn** — то есть отвечает вам в чате
вопросом и ждёт.

```
Введите код из приложения-аутентификатора для example.com
```

Ваш ответ — это обычное сообщение в чат. Браузер, страница и сессия остаются
в том же состоянии, агент продолжает с того места, где остановился.

Посмотреть, на чём агент ждёт, и забыть вопрос:

```bash
dots handover            # для профиля этой папки
dots handover NAME
dots handover NAME --clear
```

В окне `dots-gui` вопрос появляется оранжевой полосой над логом.

#### Видимый браузер

Запустите с `--headed` (или галочка в GUI) — тогда браузер открывается
окном, и код можно ввести прямо в него, не печатая его в чат:

```bash
dots --profile work --headed
```

Пока вы вводите код, агент не должен ничего нажимать. Он этого не делает:
инструкция говорит модели не кликать, не перезагружать и не переходить, пока
она ждёт, — любой из этих действий сбрасывает то, что вы набираете.

⚠️ **Код из аутентификатора не попадает в логи.** Агент вводит его через
`browser_type` в поле на странице. Но учтите: код, отправленный в чат,
остаётся в переписке беседы на диске — как и любой текст, который вы
написали. Для одноразовых кодов безопаснее видимое окно.

#### Что модель должна делать и чего не должна

Инструкция, которая уходит модели вместе с остальными (она в
`server.instructions`, то есть в каждой беседе), требует:

* спросить **один раз** и остановиться;
* не перезагружать страницу, не искать обход и не кликать наугад;
* не объявлять задачу невыполнимой;
* спросить **одним** вопросом — два вопроса это форма, а человек заполняет
  формы по одной;
* сказать в вопросе, **что** нужно, а не где застрял: «нужны шесть цифр
  из аутентификатора для example.com» отвечается за пять секунд;
* если окно браузера видимое — сказать, что можно ввести код прямо там, и
  ждать, не трогая страницу.

### headed vs headless

По умолчанию браузер работает в headless-режиме (без окна). Чтобы
посмотреть, что делает агент, добавьте `--headed`:

```bash
dots --headed --openrouter-key sk-or-...
```

## 10. Сессии и где что хранится

`dots` хранит две вещи в двух местах:

- **Беседы** — в `<HOME>/invisible-playwright-mcp/chats/<id>.json`.
- **Браузеры (cookies, скриншоты)** — в
  `<HOME>/invisible-playwright-mcp/sessions/<id>.json`.

И, если вы пользуетесь профилями, ещё одно место:

- **Профили и логины** — в
  `<HOME>/invisible-playwright-mcp/profiles/`.

`<HOME>` зависит от ОС:

| ОС | Путь |
|----|------|
| Windows | `%APPDATA%\invisible-playwright-mcp` (обычно `C:\Users\<you>\AppData\Roaming\invisible-playwright-mcp`) |
| macOS | `~/Library/Application Support/invisible-playwright-mcp` |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/invisible-playwright-mcp` |

Переменная `INVISIBLE_MCP_HOME` перебивает путь целиком — удобно для
тестового окружения и для хранения сессий на отдельном диске.

Каждая беседа (chat) — это отдельный серверный процесс, отдельный
браузер, отдельный фингерпринт. Беседы стартуют лениво, по первому
обращению — в колонке слева имена подгружаются мгновенно, а процесс
поднимается только когда вы открываете конкретный чат.

## 11. Использование из ассистента (MCP)

`dots` запускает на порту `8765` HTTP-сервер, который выглядит для
обычного браузера как обычный сайт. Но сам `invisible-playwright-mcp`
может работать и как MCP-сервер по stdio — для Claude Code, Codex,
Gemini CLI и любого MCP-клиента.

Чтобы встроить браузер `dots` в ассистент, есть
[invisible_playwright_mcp](https://github.com/feder-cr/invisible_playwright_mcp).
Этот пакет поднимает тот же движок в режиме MCP и предоставляет его
как сервер инструментов.

```bash
uvx --from invisible-playwright-mcp invisible-playwright-mcp
```

В Claude Code:

```bash
claude mcp add invisible-browser -- uvx invisible-playwright-mcp
```

После этого ассистент видит инструменты `browser_*` (полный список в
следующем разделе) и может ими пользоваться.

## 12. Инструменты MCP-сервера

Когда `dots` подключён к ассистенту как MCP, модель получает набор
инструментов. Все они принимают аргумент `browser` (`main` или
`support`, по умолчанию `main`).

### Управление браузерами

| Инструмент | Что делает |
|------------|------------|
| `browser_open` | Открыть `main` или `support`. С параметрами `seed`, `proxy`, `profile` — сменить идентичность. |
| `browser_close` | Закрыть один из двух браузеров. |
| `browser_list` | Какие браузеры открыты и где каждый. JSON. |
| `browser_status` | Текущая идентичность, прокси, профиль, URL. |

### Чтение страницы

| Инструмент | Что делает |
|------------|------------|
| `browser_navigate` | Перейти на URL. Возвращает HTTP-статус и фактический URL после редиректов. |
| `browser_read_text` | Видимый текст элемента (по CSS-селектору). Обрезается до 6000 символов с пометкой. |
| `browser_snapshot` | Интерактивные элементы страницы с готовыми селекторами. Используйте их в `browser_click`/`browser_type` как есть. |
| `browser_read_html` | HTML-структура страницы, очищенная от шума. Режимы: `form` (формы и подписи), `text` (только текст), `full` (структура без атрибутного мусора). |
| `browser_take_screenshot` | PNG-снимок страницы. |
| `browser_watch` | Живой JPEG окна браузера (рамка, табы, адресная строка). Не использовать для координат клика — они от всего окна, не от страницы. |

### Действия на странице

| Инструмент | Что делает |
|------------|------------|
| `browser_click` | Кликнуть по CSS-селектору. Используйте селектор из `browser_snapshot`. |
| `browser_click_at` | Кликнуть по координатам `(x, y)` в области видимой страницы. Полезно для canvas-капч и слайдеров. `hold_seconds` — удержание. |
| `browser_type` | Вписать текст в поле (заменяет значение). Не эмулирует пошаговый ввод — для автокомплита используйте `browser_click` + `browser_press_key`. |
| `browser_select_option` | Выбрать опцию в `<select>` по видимой подписи или `value`. |
| `browser_press_key` | Нажать клавишу: `Enter`, `Tab`, `Escape`, `ArrowDown`, `Control+a`, или одиночный символ. |
| `browser_evaluate` | Выполнить JavaScript в странице и получить результат. **Только чтение.** Попытка изменить страницу отклоняется с указанием правильного инструмента. |

### Профили и логины

| Инструмент | Что делает |
|------------|-----------|
| `dots_profile_list` | Какие профили сохранены. Без паролей. |
| `dots_profile_show` | Подробности одного профиля: каталог, выход, seed, устройство, рабочая папка, сайты с логинами. |
| `dots_profile_use` | Закрыть браузер (`main` или `support`) и открыть его под именем профиля. |
| `dots_profile_save` | Создать профиль или изменить один из его параметров (`pin` — устройство, которое он заявляет). |
| `dots_profile_check` | Проверить, что открытый браузер — то самое устройство, которое заявляет профиль. |
| `dots_ask_operator` | Остановиться и спросить человека то, что есть только у него (код из аутентификатора, подтверждение платежа, CAPTCHA). |
| `dots_auth_list` | Сайты, для которых сохранён логин. Паролей в ответе нет. |
| `dots_auth_get` | Логин и пароль для одного сайта — чтобы ввести их в форму. |
| `dots_auth_signin` | Заполнить форму входа сохранённым логином и нажать кнопку. |
| `dots_auth_save` | Запомнить логин (только если об этом попросили). |
| `dots_auth_forget` | Удалить сохранённый логин. |

Пример задачи, которая их использует:

> Зайди на `https://shop.example.com`, войди под сохранённым логином для
> этого сайта, найди заказ с номером 4417 и выпиши его статус и сумму.

## 14. Устранение неполадок

### «no OpenRouter key» при запуске

Не найден ключ модели. Задайте `OPENAI_API_KEY` или
`OPENROUTER_API_KEY` в шелле, в `.env`, либо передайте
`--openrouter-key`. См. раздел 4.

### Браузер не открывает страницу / зависает на загрузке

Проверьте:

- доступ к `OPENAI_BASE_URL` — например, для локального Ollama:
  `curl http://127.0.0.1:11434/v1/models`;
- имя модели (`OPENAI_MODEL`) — у провайдера оно может называться
  иначе, чем у OpenRouter.

### Движок браузера не скачивается

Первый запуск качает ~150 МБ. Если нет интернета или прокси мешает,
используйте `--binary PATH` и предварительно скачанный бинарник.

### Ошибка авторизации 401/403 у провайдера

Проверьте ключ — он мог истечь или быть в неправильной переменной.
Запустите `dots --help` и убедитесь, что не указан устаревший флаг.

### Два запроса одновременно

Не поддерживается. Один браузер = одна пара рук. Если нужен второй
параллельный сценарий — откройте вторую вкладку `http://127.0.0.1:8765`
в браузере: каждая вкладка получает свой чат со своим фингерпринтом.

### Логи в Linux уходят в /dev/null

`stdout` используется MCP-каналом, когда `dots` запущен как MCP-сервер.
В режиме UI всё нормально — пишется и в stdout, и в stderr.

### Старые строки прогресса остаются в терминале

`dots` рисует прогресс скачивания браузера на одной строке
(carriage return). На неродном терминале (CI, log-файл) — это просто
много строк; ничего не сломано.

### Сессии переехали

После переименования проекта `dots`/старого названия сессии
автоматически переезжают из `~/.local/share/aihawk` в
`~/.local/share/invisible-playwright-mcp` при первом запуске. Если
хотите откатить — установите `INVISIBLE_MCP_HOME` вручную.

## 15. Безопасность

Ключ модели — это пароль к деньгам. Несколько вещей, которые `dots`
делает ради него:

- **Ключ не уходит в браузер.** Запускаемый браузер получает
  переменные, в которых `OPENROUTER_API_KEY` уже нет, а любая другая
  переменная с тем же значением тоже вырезана. Так сделано не для
  скрытности, а чтобы движок, который логирует свой environment при
  падении, не показал ключ на серверах телеметрии.
- **Ключ из `--openrouter-key` не попадает в environment вообще.** Его
  читает тот, кому он нужен, и больше никто. `.env` в дочернем процессе
  снимается тем же фильтром.
- **В логах — только имена, не значения.** `dots` пишет «env: `.env`:
  OPENAI_API_KEY», а не сам ключ. Случайно скопировать в тикет или
  терминал нечего.
- **Шифрования диска нет.** Cookies и логины в `profile-dir` лежат как
  есть. Если это критично — зашифруйте раздел или положите профиль в
  зашифрованную папку.

Когда ставите `dots` на сервере или в Docker — `--host 127.0.0.1` остаётся
по умолчанию и слушает только loopback. Не меняйте его, не убедившись,
что за `127.0.0.1` действительно стоит доверенная среда.

## 16. Серверный режим: API для приложений

Интерфейс — это страница для человека. Приложению, которому нужны данные с
сайта, нужна дверь, и `dots serve` — это дверь: тот же браузер, тот же
профиль, тот же движок, только через HTTP.

```bash
dots serve --host 0.0.0.0 --port 8080 --api-key sk-...
```

Собственные двери интерфейса при этом закрываются, а двери API — открываются
вместо них. Это сделано намеренно: интерфейс умеет отправлять задание
браузеру и показывать картинку окна, в котором выполнен вход в аккаунт, и
ни одна из этих дверей ключа не спрашивает.

### Двери

| Дверь | Что делает |
|-------|------------|
| `GET /api/v1/health` | жив ли сервер — единственная дверь без ключа |
| `GET /api/v1/status` | модель, профиль, устройство, вопрос, на котором ждём |
| `POST /api/v1/run` | задание и ответ на него |
| `POST /api/v1/tasks` | задание и id, по которому можно вернуться |
| `GET /api/v1/tasks/{id}` | чем кончилось задание |
| `GET /api/v1/tasks/{id}/events` | то же, но по ходу дела (SSE) |
| `GET /api/v1/sessions` | беседы, которые держит этот сервер |
| `POST /api/v1/sessions` | новая беседа под вашим именем |
| `POST /api/v1/reset` | забыть переписку, оставив браузер |
| `GET /api/v1/handover` | вопрос, на котором агент остановился |
| `POST /api/v1/handover` | ответ на него, и работа продолжается |
| `GET /api/v1/browser` | где сейчас браузеры |
| `GET /api/v1/frame` | картинка окна браузера |
| `POST /api/v1/stop` | остановить работу в беседе |

### Задание и ответ

```bash
curl -X POST http://127.0.0.1:8080/api/v1/run \
  -H 'X-Dots-Key: sk-...' -H 'Content-Type: application/json' \
  -d '{"task": "Зайди на example.com и выпиши три самых дешёвых цены на 12-16 число"}'
```

Тело ответа:

```json
{
  "ok": true,
  "id": "r1730000000000",
  "session": "api",
  "state": "done",
  "answer": "12-го 42 EUR, 13-го 51 EUR, 14-го нет мест",
  "data": null,
  "handover": null,
  "events": [{"kind": "tool", "text": "browser_navigate ..."}]
}
```

- **`"session": "prices"`** — один браузер между вызовами: cookies, логины и
  открытая страница остаются. Без него используется собственная беседа
  сервера: она начинается пустой и не смешивается с чужой перепиской.
- **`"json": true`** — попросить ответ объектом JSON; он придёт в `data`.
  Если ответ не JSON, `data` будет `null`, а в `error` — что именно не так.
  Текст ответа при этом остаётся в `answer`.
- **`"wait": 300`** — сколько секунд ждать ответа. Если работа не кончилась,
  придёт `202` с id, по которому можно вернуться: `GET /api/v1/tasks/{id}`.
- **`events`** — всё, что агент делал, а не только последняя фраза.

Ключ передаётся в заголовке `X-Dots-Key`, в `Authorization: Bearer ...` или
в строке запроса как `?key=` — последнее нужно для потока событий
(`EventSource` не умеет отправлять заголовки) и оставляет ключ в логах
сервера. Он обязазателен, как только сервер слушает не только loopback:
`dots serve --host 0.0.0.0` без ключа не запустится.

### Когда странице нужен человек

Некоторые страницы не пускают дальше: код из аутентификатора, СМС,
подтверждение платежа, CAPTCHA. Агент останавливается и спрашивает — ответ
приходит тем же путём:

```json
{"state": "waiting",
 "handover": {"question": "Нужен шестизначный код из приложения-аутентификатора",
              "need": "шесть цифр для example.com",
              "page": "https://example.com/login"}}
```

Ответ — `POST /api/v1/handover` с `{"answer": "481902"}`. Агент продолжит с
того же места, с той же страницей и той же сессией; браузер при этом не
перезапускается.

### Что ещё стоит знать

- **Один профиль — один каталог браузера**, а Firefox не открывает один и тот
  же каталог дважды. Поэтому сервер выполняет одну задачу за раз, а браузер
  переходит к той беседе, в которой пришла новая задача. Cookies остаются
  (они лежат в каталоге профиля), открытая страница — нет.
- **Один браузер — одна пара рук.** Два задания одновременно не выполняются:
  второе получает `409`. Разные беседы — разные переписки, но браузер
  общий.
- **Каждая беседа — отдельный процесс** со своей перепиской. `POST
  /api/v1/sessions` с новым именем открывает новую.
- **Переписка растёт.** Каждый ход отправляет всю переписку заново, поэтому
  `POST /api/v1/reset` забывает её и оставляет браузер — cookies, логины и
  открытую страницу.
- **Ключ API не попадает в окружение дочерних процессов.** Он читается
  один раз тем процессом, которому нужен, и дальше лежит только в нём.
